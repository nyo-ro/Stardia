# Stardia 再設計の確定方針

決定日: 2026-10-30。ユーザーが承認した再設計方針を記録する。
段階1はv0.0.7.1。現行保存形式のまま登録入口・導線だけを整理する。
以下の新モデル・自動判定ルールは後続段階の仕様であり、段階1には実装しない。

## 利用者の操作

学習テーマを決め、学習計画で大枠から具体化し、今日の予定をチェックする。
内部の項目・予定・実績IDを理解させない。詳細時間・量・メモは将来任意。
テンプレートは自由作成・教材別・期間別から。適用後の構造は自由に編集可能。
固定の月／週／日階層、固定の学習方法は導入しない。

## 具体化状況の自動判定（実装前仕様）

判定は階層の深さ、名称の文章解析、学習時間の長さを評価しない。
「実行内容あり」は、利用者が自身の作業として入力・選択した内容と有効な学習項目参照があること。
「有効な実行設定」は単発の実在日、または対応済みの繰り返し／期間内実行設定が検証を通ること。
親の目標期間や子の予定を、親自身の実行設定へ暗黙転用しない。

優先順:
1. 自身の実行内容と有効な実行設定が両方ある → 実行可能。
2. 自身の実行内容、未完成の実行設定、有効な子計画のいずれかがある → 計画中。
3. それ以外 → 構想。名称・説明・目標期間だけでも構想として保存できる。

子が全て実行可能でも、親自身の状態は自動的に実行可能にしない。
親には「子の実行可能件数」と「自身の具体化状況」を別に表示する。
子を増やしたり深くしたりしても完成度の点数を上げない。完了済みかどうかは判定に含めない。
必要なら表示上の手動指定（auto/nullを標準）を将来設けるが、実行設定の検証を迂回しない。
有効な実行設定なしの「実行可能」への指定は拒否し、不足情報を案内する。
アーカイブ中は具体化案内・有効件数の対象外とし、内容と過去実績を保持する。

判定例:
- 「11月の学習」＋期間のみ → 構想。
- 子計画がある「11月の学習」 → 計画中（自身の作業なし）。
- 「第1章を読む」＋自身の実行内容、日付未定 → 計画中。
- 内容＋11月2日の単発予定 → 実行可能。時間未設定でも可（後続モデル）。
- 内容＋毎日20問の有効ルール → 実行可能（繰り返し実装後）。
- 実行可能な親へ子を追加 → 自身の作業・既存予定・過去実績をそのまま保持。

## 親子・進捗

親は原則整理・集計用。自身の作業を明示したときだけ実行対象。
集計は対象範囲の実行回ID集合を重複排除し、親自身と子孫を1回ずつ数える。
親へ子の集計を実績として保存しない。具体化状況と学習達成率は別指標。
子追加・移動で既存予定や過去実績を消さない。作業分割による将来予定の停止は別の明示操作。
階層はparentIdで自由に変更し、循環・自己参照・異なるprojectIdの参照を拒否する。
名称・階層だけから実績の関連先を推測しない。

## 日々のチェック

チェックはその実行回の完了情報を自動保存。解除は完了だけを取り消し、詳細実績は保持。
予定日・実施日・操作日時は別情報。過去日の入力・訂正を許可する。
旧チェックに存在しない実施日を予定日や移行日で補完しない。
詳細記録の削除は別操作。時間未設定はnullとし0分に変換しない。
保存失敗時はチェックを保存前へ戻す。競合は上書きせず、最新状態の確認を促す。
旧データの完了表示と記録時間の集計をそれぞれ維持する。

## 繰り返し・分類・テンプレート

単発と階層が安定してから実装する。週の回数指定は原則1日1回。
ルール変更はこの日以降が標準。過去の実行済み予定と実績は保持。
ルールと各回のIDを分離し、例外変更後も同じ回のIDを維持する。
分類の種類・値は計画ツリーから分離。自由作成・教材別・期間別テンプレートを優先。
同日複数回の指定は後続拡張余地を残し、暗黙には許可しない。

## 段階2で独立検証する移行契約

PlanNode／実行ルール／各回の予定／完了情報／詳細記録を分離する案を基礎とする。
具体的な保存フィールド・バージョン番号は移行対応表と検証コードで確定する。
既存StudyItem・StudySchedule・StudyRecordのID、完了、アーカイブ、全実績フィールドを保持。
旧schema 1/2と旧backup 1/2の入力を厳密検証する。不正値の自動修復・推測はしない。
旧予定は単発として扱い、繰り返しや階層を名称から推測しない。
旧完了は実施日不明を許容し、旧予定日基準の進捗を再現する。
移行前原本は世代付きで保管し、既存migrationBackupsの原本を上書きしない。
全プロジェクトの変換・原本退避・revision更新を一括確定し、失敗時は旧状態を維持。
正常、破損、未知参照、容量不足、途中失敗、複数タブ、旧タブのversionchange、再実行を検証。
バックアップの旧→新復元、新形式往復、失敗時原状維持が通るまで移行を公開しない。
既存AI JSON v1の検証を緩めない。移行前の保留JSONは古いrevisionとして拒否する。
新形式で表現できない旧操作は黙って変換せず拒否し、最新出力への再生成を案内する。

注意: 現行migrationBackupsはprojectId単位で1原本、完全復元で全消去する。
次段階では世代と保持範囲の設計が必要。旧版へのアプリ差し戻しと新データの読込互換は別。
移行前バックアップによる復旧手順を用意し、新形式の旧版読込を保証しない。

## 開発順序と停止点

1. v0.0.7.1 登録入口・操作導線（現行形式）。
2. 新モデル・安全な移行・旧バックアップ復元の独立検証。
3. 自由階層・単発予定・初回設定。
4. チェック主体、詳細任意、過去日実施。
5. 利用者による実操作レビュー。
6. 繰り返し・分類・テンプレート拡張。
7. AI連携・バックアップ通知。
8. スマホ最適化。その後公開前品質確認。

各段階で実装・回帰テスト・ブラウザ確認・ローカルコミット・報告。
段階1の報告後は移行を始めず、前段階の安定を確認して次段階へ進む。
390pxの基本操作と保存安全性は毎段階確認。公開日は未定、Push・公開は別指示が必要。
